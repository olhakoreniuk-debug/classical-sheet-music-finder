# ADR-0005: React, TypeScript and Vite for the frontend

- **Status:** Accepted
- **Date:** 2026-11-27 (revised the same day: TypeScript instead of JavaScript)
- **Changes:** replaces the earlier recommendation of plain HTML and
  JavaScript without a framework, and the first version of this ADR, which
  proposed React with JavaScript (JSX).

## Context

Assignment 2 requires a frontend that shows real stored data, with a
catalogue, a detail view, a form that displays API validation errors, and
loading, empty and error states. It must be built from `openapi.yaml`, not
from server code.

The application is expected to grow: more external music sources (IMSLP
today, OpenScore Lieder next, Open Opus for enrichment later), search, voice
categories and score previews. A growing frontend that consumes a
contract-defined API benefits from compile-time checking that its code
matches the contract.

## Decision

Use **React with TypeScript (strict) and Vite**, as a separate frontend
package in `frontend/`.

### Language and type safety

- **TypeScript in strict mode** (`"strict": true`, plus
  `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and
  `noImplicitOverride`). Components are written in **TSX**.
- `tsc --noEmit` runs as part of the frontend checks; the build fails on
  type errors.
- **API types are generated, never written by hand.** `openapi-typescript`
  generates `frontend/src/api/generated/schema.ts` from `openapi.yaml`
  (`npm run api:types`). Application code refers to the generated
  `components['schemas']['Work']`, `operations['listWorks']` and so on,
  through a small module of type aliases (`frontend/src/api/types.ts`).
  A check in the frontend tests fails if the generated file is out of date
  with `openapi.yaml`.
- The **backend and the importer stay in JavaScript.** This decision applies
  to `frontend/` only. Architecture v2's rule "no TypeScript just for
  interfaces" continues to apply to the backend.

### Boundaries and separation of concerns

| Layer | Location | Responsibility | May depend on |
|---|---|---|---|
| API communication | `src/api/` | One typed function per `operationId` (`listWorks`, `getWork`, `createWork`, `listSources`); converts Problem Details responses into one `ApiError` type with field errors; base URL `/api/v1` | generated types only |
| Application logic | `src/features/<feature>/hooks/` and `model/` | Data loading (with `AbortController`), URL-to-filter mapping, form state, mapping `ApiError` field errors to form fields | `src/api/` |
| Presentation | `src/features/<feature>/components/`, `src/components/` | Rendering and user interaction only; receive data and callbacks through props | application-logic hooks, shared components |
| Routing and composition | `src/app/` | Routes, layout, providers | features |

- The frontend talks to the backend **only through the REST API**. It never
  imports backend code and does not know which database or providers exist.
- **Provider independence:** sources are loaded from `GET /sources`; source
  names, attribution and the source filter are rendered from data. No
  provider is named in frontend code, so adding, removing or replacing a
  provider requires no change to React components.

### Structure (by feature and responsibility)

```text
frontend/
  src/
    app/                 App.tsx, routes.tsx, Layout.tsx
    api/
      generated/schema.ts   generated by openapi-typescript (do not edit)
      types.ts              aliases for generated types
      client.ts             typed functions per operationId
      apiError.ts           ApiError from Problem Details
    components/          shared presentational components: LoadingState,
                         EmptyState, ErrorState, FieldError, Attribution,
                         Pagination
    features/
      works/
        components/      WorkCatalogue, WorkFilters, WorkList, WorkDetail, WorkForm
        hooks/           useWorks, useWork, useCreateWork
        model/           filter <-> URL mapping, form values <-> request mapping
      sources/
        hooks/           useSources
    main.tsx
```

- **Routing:** React Router: `/works` (catalogue; filters, sort and page in
  the URL), `/works/:workId` (detail), `/works/new` (form).
- **Data fetching:** small custom hooks using `fetch`; no global state
  library at first (KISS). A data-fetching library can be introduced later
  through a new ADR if caching needs grow.
- **Styling:** CSS Modules (built into Vite); no UI component library.

### Accessibility and responsive design

Semantic HTML; a label for every form control; field errors linked with
`aria-describedby` and `aria-invalid`, and focus moved to the first invalid
field after a `422`; loading and status messages in `aria-live` regions;
focus management on route changes; full keyboard use; sufficient colour
contrast; text always rendered as text (no `dangerouslySetInnerHTML`, see
ADR-0003); a mobile-first layout with CSS grid and flexbox.
`eslint-plugin-jsx-a11y` and `typescript-eslint` check the code.

### Development and serving

- Vite dev server on `127.0.0.1:5173` with a proxy for `/api` to the Express
  server on `127.0.0.1:3000`, so the browser sees one origin (ADR-0003).
- For a demonstration, `vite build` produces static files that the Express
  server serves from the same origin.

### Dependencies (installed only in `frontend/`)

- Runtime: `react`, `react-dom`, `react-router`.
- Development: `typescript`, `@types/react`, `@types/react-dom`, `vite`,
  `@vitejs/plugin-react`, `openapi-typescript`, `vitest`,
  `@testing-library/react`, `jsdom`, `eslint`, `typescript-eslint`,
  `eslint-plugin-jsx-a11y`.
- Each package is verified before installation and pinned to a release at
  least two weeks old.

### Testing

Component and hook tests with Vitest and React Testing Library. Response
fixtures are taken from the examples in `openapi.yaml` and typed with the
generated types, so fixtures that drift from the contract fail to compile.
Every state is covered: loading, empty, error, success, and validation
errors shown at the right fields.

## Required updates to `CLAUDE.md` (later phase)

Not applied during the contract phase. When the frontend is implemented:

- Stack: add "Frontend: React, TypeScript (strict) and Vite in `frontend/`;
  backend and importer remain plain JavaScript."
- Commands: add the frontend commands (`npm --prefix frontend run dev`,
  `test`, `typecheck`, `api:types`), run through mise.
- Rules: "Never hand-write API types; regenerate them from `openapi.yaml`."

## Consequences

- Type errors between the frontend and the contract are caught at compile
  time; contract changes surface as compile errors in the affected code.
- Reusable components, feature folders and client-side routing support the
  planned growth.
- A build step, a type-check step and a separate set of development
  dependencies, kept out of the backend's `package.json`.
- Two languages in the repository (JavaScript backend, TypeScript frontend),
  separated by the `frontend/` package boundary.

## Alternatives considered

- **React with JavaScript (JSX) and JSDoc types:** fewer tools, but weaker
  guarantees and type checking only in the editor. Replaced by this
  decision.
- **Plain HTML and JavaScript:** harder to grow into an interactive
  application. Rejected.
- **Next.js or another full-stack framework:** server rendering is not
  needed and would couple frontend and backend. Rejected.
- **Hand-written API types:** duplicate the contract (violates DRY). Rejected.
